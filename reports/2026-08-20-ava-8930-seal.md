## The chip

Both renderers previously collapsed every unrecognised status into the gold `pending` style —
`status === "live" ? "live" : (status === "planned" ? "planned" : "pending")`. `SEALED` fell
through that last branch, so a sealed row read as *pending* in amber. It now has its own class.

| | Spec | Rendered |
|---|---|---|
| Background | `#2EE6A8` | `rgb(46, 230, 168)` |
| Text | `#14161C` | `rgb(20, 22, 28)` |
| Border | `#2EE6A8` | `rgb(46, 230, 168)` |
| Dot | — | `rgb(20, 22, 28)`, glow removed |
| Contrast | ≥4.5:1 | **11.19:1 — AA and AAA** |
| Box | — | `74×24` at both 390 and 1280 |

`#2EE6A8` is CIRCULANT Booked-Green and `#14161C` is Ink, both straight out of CLAUDE.md § 2 —
no new colour entered the system. This is the only **filled** chip in the family; `live`, `pending`
and `planned` are all tinted outlines. That is the point: sealed is terminal, not a running state.

Both mappers now lowercase before matching, so `SEALED` / `Sealed` / `sealed` all resolve.
`live` / `planned` / `pending` behave exactly as before.

## THREE THINGS THE RENDER GATE FOUND

### 1. Nothing renders `ava-8930-tune`, and the previous readback said otherwise

`/hq` reads **`b.lanes` only**, against eight hardcoded `.lane[data-lane]` rows
(L1, L2, L3, L4, L5, drip, ads, content). It never touches `b.items`.
`/work` reads `b.items`, but only for eleven hardcoded `data-id` cards:

```
brand · hq · voice-ab · work-ads · work-elevenlabs · work-emails
work-links · work-prompts · work-social · work-social-run1 · work-todo
```

`ava-8930-tune` is in neither list. The `SEALED` flip is **data-only — invisible on both pages.**

The prior run's readback claimed the chip "reads SEALED in gold" on `/hq` and that `/work` would
not show it. That was backwards, and it came from applying the *lane* mapper to an *item* in a
simulation instead of rendering the page. **Corrected here.** The chip work in this commit is
correct and future-proof, but until a **lane** carries `SEALED`, `/hq` shows no green chip.

Proven by driving a real `SEALED` lane through the real page rather than reasoning about it — see
the gate table below.

Two further rows are in the JSON with no markup to land in: lanes `L8` and `prospects` have no
`.lane[data-lane]` row on `/hq` either. Pre-existing, unrelated, noted for whoever touches this next.

### 2. `latest_published` was never a field on this row

It is **not a JSON key anywhere in `board.json`** — every occurrence is prose inside a `label` or a
`log` entry. `ava-8930-tune` carried no `latest_published` and contained no `v43`.

The only two `v43` sites in the whole file are `POSTCALL-RAIL-8930`'s label and its matching log
entry, both historical records of the 2026-08-18 rail run, where the surrounding sentences read:

> "LLM v42 and v43 are BYTE-IDENTICAL" … "ROLLBACK: pin inbound\_agents to agent\_version 42"

Rewriting `v43` → `v48` there would have made those sentences false and corrupted an audit record.
So `latest_published: "v48"` was **added** to the row named in the brief, and the two `v43` sites
were left alone. This makes `ava-8930-tune` the only one of 45 items with a sixth key; nothing reads
it, so it is inert data, not a rendering risk.

### 3. `/hq` has a pre-existing horizontal overflow at 390

Every lane row is **585px wide inside a 375px client width**; document `scrollWidth` is **601**.

Measured against `HEAD` *before* this change, by serving the unmodified file side by side:

| | Baseline (pre-change) | After |
|---|---|---|
| `document.scrollWidth` at 390 | **601** | **601** |
| Every lane row width | **585** | **585** |

Identical. **Not introduced here, and not fixed here** — it is a `.lane` flex-layout issue driven by
the very long lane notes, it predates this run, and `/hq` is a gated internal page. It does violate
the zero-horizontal-scroll-at-390 rule and should get its own pass.
